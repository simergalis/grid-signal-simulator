Here's a Ray → WorkloadSignal example, built against the Section 10 input data contract in the spec.

Example: Ray job scaling event

A Ray cluster autoscaler adds workers to a running training job — this fires a scale event.

json
{
  "job_id": "raysubmit_8f3a1c2e9b4d7f10",
  "event_id": "evt_01J8X7QK3M5N6P8R9T2V4W6Y8Z",
  "event_type": "scale",
  "timestamp": "2026-08-12T14:32:07.481Z",
  "hardware_profile_id": "nvidia-h100-sxm5-8way",
  "node_count": 12,
  "workload_class": "training",
  "site_id": "site-us-east-04"
}
Example: Ray Serve inference deployment, steady state

Inference workloads carry the conditional queue_depth / request_rate fields (Section 6, row 2 — micro-ramp modeling needs them):

json
{
  "job_id": "serve_deployment_llama3-70b-endpoint",
  "event_id": "evt_01J8X7RT9K2M4N6P8Q1S3U5W7Y",
  "event_type": "running",
  "timestamp": "2026-08-12T14:33:19.902Z",
  "hardware_profile_id": "nvidia-h100-sxm5-8way",
  "node_count": 4,
  "workload_class": "inference",
  "site_id": "site-us-east-04",
  "queue_depth": 143,
  "request_rate": 87.4
}
Field-by-field, with the Ray-side source
Field	Type	Req'd	Ray adapter source
job_id	string	Yes	Ray's submission_id (Jobs API) or Serve deployment name — must stay stable across the job's full lifecycle, not per-task
event_id	string	Yes	Adapter-generated (e.g. ULID), one per emitted event — this is what Section 17.1's idempotency dedupe key rides on
event_type	enum	Yes	Mapped from Ray job/actor status transitions — see mapping below
timestamp	ISO-8601 UTC	Yes	Source-clock time of the underlying Ray status transition, not adapter receipt time (Section 11.4 skew handling assumes this)
hardware_profile_id	string	Yes	Derived from the Ray node's resource spec / accelerator type; unmapped GPU SKUs fall through to the Section 5.1 fallback profile
node_count	integer	Yes	Active Ray nodes/workers backing the job at event time. A scale event carries the new total, not a delta
workload_class	enum	Yes	training for Ray Train jobs, inference for Ray Serve deployments, other for ad hoc Ray Core jobs that don't fit either
site_id	string	Yes	Static per-cluster config in the adapter, not derived from Ray
queue_depth / request_rate	number	Conditional	Pulled from Ray Serve's autoscaling metrics (pending requests / requests-per-second) — only required when workload_class = inference
Ray status → event_type mapping

Ray doesn't have a native enum that lines up 1:1 with the WorkloadSignal contract, so this is adapter-layer logic, not something Ray exposes directly:

Ray state	event_type
PENDING (Jobs API)	queued
RUNNING (first observed)	starting
RUNNING (subsequent ticks)	running
Autoscaler adds/removes workers on a running job	scale
Ray Train checkpoint callback fires	checkpoint_start / checkpoint_end
SUCCEEDED / FAILED	job_end
STOPPED (user-initiated)	cancelled

A few things worth flagging given how the spec constrains this:

event_id uniqueness is on the adapter, not Ray. Ray doesn't emit a stable per-event ID, so the adapter has to generate one and needs to guarantee it's unique per emitted event — not per Ray-side status poll — or you'll get spurious idempotency collisions.
Checkpoint detection for Ray Train isn't automatic — it depends on the adapter hooking Ray Train's checkpoint callbacks. If that hook isn't wired up, checkpoint events won't fire at all, which (per Section 6.2) just falls back to the power-shape heuristic for checkpoint-valley classification rather than failing outright.
Any event missing a required field or with an out-of-domain value (e.g. negative node_count) gets quarantined per Section 17.2, not silently dropped — worth designing the adapter's error path around that structured rejection rather than swallowing failures.
