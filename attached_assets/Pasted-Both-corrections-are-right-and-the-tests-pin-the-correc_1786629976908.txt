One more instance of the same bug class, though, before Phase 3 opens — this one bigger in dollar terms than the BESS gap was.

Grid TOU repricing has the identical scope problem BESS just had. The stated rationale for Correction B is "TOU is tick-context-dependent — it correctly lives in step()." True, but that means grid sources are only repriced when rank() is called from inside step(). §4.3's escalation branch calls PowerRanker.rank() directly, restricted to confirm/human_only sources — the same call site that had the BESS problem. Nothing in this correction touches that path for grid. So: a grid_spot or grid_reserved source sitting at confirm/human_only tier, shown to a real operator via §4.3's advisory or fed to PMSTestDouble, gets ranked using whatever marginal_cost_mwh its caller happened to attach — not the tick's actual _season_from_month(month) + hour_of_day TOU rate.

That's a wider swing than the BESS case was. BESS was a fixed $38 vs. whatever a caller guessed. Grid TOU spans $58.72 to $177.02 across the six periods you just tabulated — a wrong value here isn't just imprecise, it can flip which source an operator thinks is cheapest, in the exact advisory path that exists to inform a human decision under §4.3's "GridSignal's involvement ends at publication" rule. If the number published is wrong, there's no downstream check catching it before the operator acts on it.

The fix is the same shape as Correction B: pull _pge_price_for_period(hour_of_day, month) out of step() into something callable on its own — a public repricing function that both step() and whatever assembles the §4.3 confirm/human_only advisory can call with the tick's actual t_s-derived hour_of_day/month. Don't duplicate the six-key lookup at a second call site; that's a second source of truth for the same fact, which is the thing this doc's already spent two rounds correcting. Add a test_grid_confirm_tier_priced_correctly_for_tick_context alongside the BESS one once that's in place.

This doesn't block Phase 3 — BudgetGate per §3.3 doesn't touch pricing or rank() at all, so it can proceed in parallel. It does need to land before Phase 4 wires §4.1's escalation branch for real, since that's the first point this bug becomes reachable. Flag it now rather than after Phase 4's report, since catching it there would mean unwinding wiring that assumed the gap didn't exist.
