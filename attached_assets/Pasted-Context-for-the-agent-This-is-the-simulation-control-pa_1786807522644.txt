Context for the agent: This is the simulation control panel for the GridSignal demonstration simulator (Simulator Functional Spec, referencing Forecast Engine Spec §22.3/ST-4). The simulator runs on a simulated clock that is not wall-clock time, and control-relevant timers (checkpoint-valley classification windows, dedupe windows, staging holds) are persisted explicit state keyed to that simulated clock — never cache TTLs, never derived from wall time. Do not violate that.

Goal: Add a PAUSE control to the existing START/STOP simulation controls, with a defined state machine and explicit timer-freeze semantics.

State machine:

States: STOPPED → RUNNING → PAUSED → RUNNING → ... → STOPPED
STOPPED: no simulated clock advance. START begins/resumes a run.
RUNNING: simulated clock advances on tick; PAUSE and STOP both available.
PAUSED: simulated clock is frozen — no ticks processed, no timers advance, no events dispatched. Only START (resume) and STOP (end) are available. PAUSE is disabled/hidden.
On PAUSE: capture and persist the exact simulated-clock timestamp at which the pause occurred, plus the state of any in-flight timers (checkpoint-valley classification windows, staging holds, dedupe windows) as of that instant — same mechanism §22.3 uses for restart reconstruction, not a new one.
On resume (START from PAUSED): the simulated clock continues from the frozen timestamp. In-flight timers resume with their remaining duration intact — a timer must not gain or lose time because of a pause, the same invariant TC-35 enforces across restarts.
On STOP (from RUNNING or PAUSED): simulation ends, state resets to STOPPED, all in-flight timer state is discarded (not persisted for a future resume — STOP is a hard end, distinct from PAUSE).

UI requirements:

PAUSE button appears next to START, enabled only while RUNNING.
While PAUSED: label the state clearly (e.g., a "PAUSED" indicator, not just an inferred button state), and freeze all displayed simulated-time readouts at the pause instant — dashboards must not show a moving clock or advancing counters while paused.
STOP is available in both RUNNING and PAUSED states.

Do NOT:

Do not implement pause as a UI-only freeze that keeps the backend tick loop running underneath (no ticks may be processed or timers advanced while PAUSED — verify this with a test, not by inspection).
Do not use wall-clock elapsed time anywhere in resume logic. Only the simulated clock and persisted timer state matter.
Do not let STOP silently reuse the PAUSE code path or vice versa — they have different persistence semantics (STOP discards, PAUSE preserves for resume).
Do not touch any southbound/dispatch code paths — this is a simulator control-plane UI change only.

Acceptance criteria:

Start a run, let a checkpoint-valley-style timer (or any multi-tick timer in the simulator) begin, PAUSE mid-timer, wait (real time) several seconds, RESUME — timer's remaining duration is unchanged from the instant of pause.
PAUSE, then STOP — simulation fully resets; a fresh START begins a new run with no residual timer state from the paused run.
While PAUSED, no simulated-clock ticks are logged/processed (verify via tick counter or event log, not visual inspection).
UI state (button enablement, PAUSED indicator, frozen readouts) matches the state machine above in all three states.

Stop and report if: the simulator's current tick loop architecture doesn't cleanly support suspending without also touching the timer-persistence mechanism from §22.3 — report back with what you find before restructuring that shared code path.
