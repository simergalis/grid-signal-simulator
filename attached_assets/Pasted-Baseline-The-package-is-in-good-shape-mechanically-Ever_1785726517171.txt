The Honolulu bug — found it

I reproduced it against runtime/solar_sim.py. At the screenshot's instant (16:58:54 HST ≈ 02:58 UTC), for Aug 2:

lat=21.31, utc_offset=-10  (Honolulu)   → fraction 0.360   ← correct
lat=32.72, utc_offset=-8   (San Diego)  → fraction 0.000   ← what you saw

San Diego at that UTC instant is 18:58 local — just past sunset. The physics model is fine. The run was computed for San Diego while the header rendered Honolulu.

The mechanism is api/app.py:118:

python
application.state.site_location = SiteLocation()   # San Diego, 32.72, -117.16, -8.0

PUT /api/location writes only to request.app.state.site_location (location.py:349). Nothing persists it. start_prod.sh says so explicitly — "All state is in-process… A restart clears in-flight runs" — but the consequence for site location wasn't followed through. Replit restarts on publish, on sleep/wake, and on any crash-restart. After any of those, the server is San Diego again while a long-lived browser tab still holds Honolulu in React state (LocationPicker.tsx:226 fetches /api/location on mount only, never re-polls).

So the failure is: header from client state, physics from server state, the two diverged silently. It will reproduce every time the process restarts under an open tab, and it will look intermittent, which is why it's worth fixing properly rather than by retry.

Three things to change:

Persist site location. You already have a site table in gridsignal.db with zero rows. Write it there and read it back in the lifespan handler. This is the actual fix.
Stamp the location into the tick payload — site_name, site_lat, site_utc_offset_h — and have the header render that, not the client's copy. Then the header physically cannot disagree with the physics. This is the cheaper and more valuable of the two, because it converts a silent divergence into an impossible one.
Log the resolved site at run start. _log.info("solar_sim: physics profile (lat=%.2f, utc%+.1f)...") already exists in _physics_samples but nothing logs which site runs.py actually resolved. One line at runs.py:162 would have made this a 30-second diagnosis.

Related, while you're in there: runs.py:152 uses DST-aware current_utc_offset_h(loc), but solar.py:92 uses raw loc.utc_offset_h. The preview panel and the run it previews will disagree by an hour for eight months of the year at any DST site.

The bigger finding: the solar tile isn't measuring anything

This is the item I'd rank above the Honolulu bug, because the bug is a one-line-ish fix and this is a design problem.

core/simulation_core.py:752:

python
p_expected_mw=p_renewable_mw,
banks_reporting=20,

exp is a copy of actual. 20 of 20 banks reporting is an integer literal. Both render on the SLD tile in the visual language of telemetry.

The consequences:

exp 0.00 MW in your screenshot was not independent evidence. I initially read it as the strongest signal that the expectation model had failed. It's a tautology — it would have read 0.00 no matter what.
Measured/expected ≡ 1.0 on the tick path. Everything §4.1 exists for — degradation detection, performance ratio, the four-state classifier's ratio >= 0.92 / >= 0.05 thresholds — is structurally unreachable there. renewable/solar.py implements all of it correctly, with hysteresis and reason codes, but that's a different model with different state, ticked separately at 1 Hz from the app lifespan.
A total inverter trip and a dead input render identically. Per §7.1.1 a renewable collapse is a Δt_lead = 0 supply shortfall that must trigger the same reserve check as a compute step. The tile can't express the difference.

Two solar models is defensible for now — the console has per-bank detail the run loop doesn't need. What isn't defensible is one tile silently mixing scalars from both. Either route p_expected_mw / banks_reporting from SolarSim.snapshot() (which computes both honestly), or render them as — on the run path and label the tile as summary-only. The snapshot() run-sync block at renewable/solar.py:~1000 is already doing acrobatics to reconcile the two — proportional scaling, a fault-suppression guard, a night-zeroing special case with the comment "run says zero is authoritative regardless of individual bank states". That block is where the two models' disagreement is being papered over, and it's the thing I'd most want simplified before a demo.

Worth adding to the acceptance matrix: assert p_expected_mw != p_renewable_mw under an injected string fault. It fails today.

CI cannot currently pass

Four independent blockers in .github/workflows/ci.yml:

No JWT_SECRET in env:. Gates 1, 5, and 8 import api.app. All three fail at collection.
--timeout=120 without pytest-timeout. Gate 1 exits on unrecognized argument.
Dependency install is a lie. pyproject.toml declares exactly one dependency (websockets), so pip install -e ".[dev]" installs nothing useful and falls through to the hardcoded list — which omits sqlalchemy, aiosqlite, bcrypt, passlib, and python-jose. The 2>/dev/null || true then swallows the failure so it surfaces as a confusing ImportError three steps later. I hit all of these installing by hand.
Gate 6 never fires. contains(github.event.head_commit.modified, 'core/') — modified is an array of full paths and contains() on an array is exact-element matching, not substring. It will never match 'core/'. Your NFR gate has been dormant.

Also: no frontend job at all. Four vitest suites exist (smoke_panels, smoke_readiness, smoke_charts, verdict_band) and package.json has no test script, so npm test fails and CI never typechecks or builds the dashboard. frontend/dist/ is committed as a prebuilt artifact with no gate proving it matches src/.

Gates 2–5 are strict subsets of Gate 1, which already ran the whole suite. Harmless, but it makes the eight-gate framing look stronger than it is — it's really four distinct checks.

Determinism gate has a blind spot

It verifies A == B within a scenario. It doesn't verify that different scenarios differ. Across the nine seeded scenarios there are only six distinct dispatch hashes, with four sharing f33094cadb63:

demo-20mw, demo-alert, demo-maintenance, demo-ramp-relax  → identical 60-tick traces

demo-maintenance and demo-ramp-relax exist specifically to exercise maintenance derating and ramp relaxation. If their traces are byte-identical to demo-20mw, those features aren't reaching dispatch in the seeded configuration — or the scenarios don't actually configure them. One added assertion (len(set(hashes)) == len(scenarios)) turns this into a caught regression instead of a green check mark.

Packaging
gridsignal_sim/gridsignal.db is in the archive. One auth_user row: sec4-operator@example.com, role operator, is_active=1, empty password_hash. Nothing exploitable — verify_password won't match empty — but a database in a release tarball is how a stale account ships to production. Add to .gitignore, seed via a bootstrap script.
README describes v2.1, package is v2.2. It calls gridsignal_sim/ "the skeleton, UNMODIFIED" and lists ten passing tests. There are 763, a full React frontend, auth, and sixteen build steps. It references GridSignal_Replit_Build_Plan_v2.1.md; the file is _v2.2.md. Anyone onboarding from this README will be badly misled about what they're looking at.
docs/ is duplicated at root and under gridsignal_sim/, with Build_Plan_v2.2.md in both. Two copies of a build plan will diverge.
IrradianceProfile.fraction_at is zero-order hold. Fine for scripted step stressors, but the physics path emits 20–120 samples of a smooth curve, and ZOH turns each into a discontinuity. On a long run those are indistinguishable from the genuine renewable-step events §7.1.1 wants the reserve check to catch. Linear interpolation for generated profiles, ZOH retained for scripted ones.
Suggested order

Wire p_expected_mw / banks_reporting honestly, add the fault-injection assertion
