Existing callers of step(). Check the simulator harness, not core//runtime/ — this is exactly the case §1 called out: EconomicDispatchLoop was "built afterward, directly in code, with no corresponding spec section," meaning a pre-002 version likely already has a harness or demo script calling it positionally. Grep the whole repo (not just the new tree) for EconomicDispatchLoop( and .step(. In particular:

test_d10_demo_20mw_bess_fires_and_tapers is the one to look at first. A BESS-firing-and-tapering demo test is precisely the kind of code that would call EconomicDispatchLoop.step() from outside this tree, and it's failing right now, on a move that was supposed to change no public interface. "Pre-existing, unrelated" is an assumption, not a finding — before Phase 2 touches this signature further, get the actual failure output. If it's failing because it's calling the old positional interface and something already shifted under it, that's not unrelated, that's the first caller you were looking for, and it changes what "before Phase 2" means here.

Make the new signature keyword-only. tick_duration_hours is being inserted second and month fourth — both in the middle of an existing positional argument list. A stale positional caller won't raise ImportError, it'll silently receive the wrong values in some arguments (whether that surfaces as a TypeError depends on luck with argument types, and float/int won't always save you). Given the parameter-catalogue discipline this project already holds itself to around silent wrong-looking-correct behavior, I'd add a bare * after t_s in the new signature so any surviving positional caller fails loudly and immediately rather than quietly computing wrong costs. Cheap to add now, before there's a second caller to migrate.
