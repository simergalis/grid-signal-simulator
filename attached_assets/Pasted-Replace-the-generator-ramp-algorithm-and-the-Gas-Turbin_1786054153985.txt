The target behaviour in one sentence: generators start one at a time, incrementally increase output, and level off at a stable state; on the way down they incrementally decrease output, unload to minimum stable load, open their breakers, and level off.

Part 1 — Backend: replace the ramp algorithm
What is wrong now

1. Simultaneous starts. core/dispatch.py _stage_for_predicted_step computes _n_start = min(max(1, ceil(delta / rated) + 1), len(_offline)) and loops stage_target() over the slice. Every unit goes OFFLINE → RAMPING on the same tick. This is the defect that opened this work.

2. Stop is a trip. core/asset_modules.py, in stage_target() on the target_mw <= 0 path, sets _target_mw = 0.0, _current_output_mw = 0.0, state = OFFLINE in one tick. That models a breaker opening on load — a fault, not a shutdown. There is no unload sequence anywhere in the codebase.

3. Two control paths. advance() drives RAMPING units toward _target_mw, captured once at stage_target() and never revised. apply_loading() drives SYNCHRONISED units toward the live fleet setpoint. Handoff is math.isclose(_current_output_mw, _target_mw). If demand moves away from the captured target the handoff can defer indefinitely, while dispatch.py sums RAMPING output into turbine_output_mw via is_synchronised the whole time.

4. Transition-tick double write. advance() runs before _synchronised_units is rebuilt in the same tick, so a unit promoted RAMPING → SYNCHRONISED has its output written by advance() and again by apply_loading(). _check_loading_exclusion tests set membership, so both writes are individually legitimate and it does not fire.

5. Cold start bypassed by design. core/simulation_core.py uses stage_target() rather than command_start(), with a comment stating that cold-start counters "would outlast a typical 300 s demo run". The demo duration is being fixed by removing the start time.

6. Commitment reads measurement, not forecast. _DISPATCH_HEADROOM_FRAC = 0.20 is an inline literal — and now also a Guard D violation waiting to happen. The trigger is turbine_output_mw / _sync_rated_mw, where the numerator includes RAMPING and AT_TARGET via is_synchronised and the denominator counts state == SYNCHRONISED only.

7. Proportional sharing. core/loading.py allocates shares = rated_i / Σ rated across all on-bus units — the policy §7.1.3.4 rejects (D-14). Changing it moves numbers on every scenario.

Phase D — commitment

Implement evaluate_commitment() and replace the headroom block in simulation_core.py entirely.

Reserve floor (primary, always binding): Σ rated over SYNCHRONISED ≥ P_dispatch_required + max(rated over SYNCHRONISED).

Commit when the floor is violated, forecast to be violated within Δt_lead, or U ≥ commit_utilisation sustained 30 s.

Decommit the last-committed unit only when all hold, sustained 300 s: floor satisfied without it; U ≤ 0.50 with it; U ≤ 0.70 without it; t_min_run_s satisfied. Where the two conflict, the floor governs. The 30 s / 300 s asymmetry is normative.

Sequential starts. At most one unit in STARTING; next command no earlier than inter_start_settle_s after the previous reaches SYNCHRONISED. Use command_start(), never a direct state assignment.

Remove the cold-start bypass. Raise TurbineConfig.hot_start_s from 60 to 300 (D-08) — and note the UI hardcodes 60 in the thermal guide, which must move in the same commit.

Add TC-89 … TC-93 per the §7.1.3 §16.14 draft, renumbered from TC-87.

Phase E — stop sequencing, loading policy, physical constraints

Stop sequence: SYNCHRONISED → UNLOADING (setpoint forced to MSL, tracking at r_asset) → levelled-off → breaker opens → OFFLINE, t_min_down_s starts. levelled_off is a derived predicate, never a TurbineState.

Sequential stops (D-09): at most one unit in UNLOADING at a time, with a settling interval. Without this, three breakers open within ten seconds — the mirror image of the defect that opened this work.

Loading policy (D-14): replace proportional sharing with sequential base-loading — units loaded toward rated in commitment order, every unit at or above MSL, residual to the marginal unit.

Enable the constraints: p_min_stable_frac 0.0 → 0.40, t_min_run_s 0.0 → 1800, t_min_down_s 0.0 → 900. All three are already enforced; only defaults change. Catalogue each. This moves numbers across many scenarios — do it last and alone.

§7.2 amendment (D-10): the breaker-open MSL step is a bridging duty on the way down. Extend the step-4 reserve check to cover it.

Add TC-94 … TC-97.

Defects to locate and fix

U-1. Aggregate ramp label contradicts its arithmetic. deriveFleet computes an aggregate ramp as maxRamp × units.length over all units — OFFLINE, STARTING and hot-standby included — using the fleet maximum rate rather than per-unit rates. The subtitle beside it claims "SYNCHRONISED only — starts excluded". Both cannot be true.

U-2. The aggregate row mixes two sources. rampEnergyMW = tick.ramp_capability_mw ?? (aggRampMWs × horizonS) — value from the backend, rate beside it from the frontend formula, and they disagree. tick.ramp_capability_mw is the sole authoritative source; delete the fallback and the frontend aggregate.

U-3. Single-unit ramp is unclamped by rated capacity. The "Ramp with 1 unit" row renders rate × horizonS with no clamp — 0.300 MW/s × 110 s = 33 MW from a 15 MW machine. Clamp to rated_mw, and derive it from the same function as the aggregate row so the two cannot diverge.

U-4. N−1 firm capacity counts units that are not there. n1FirmMW = installedMW − maxUnitMW uses installed capacity, so an OFFLINE unit contributes to firm capacity. After Phase D this must be computed from committed units and reconciled against the §7.1.3.3 reserve floor — the two are answering the same question and must not disagree.

U-5. Start times hardcoded in three places. _THERMAL_ROWS, _thermalSub, and the Cold-start sync stat row hard-code 60 / 300 / 900 s. These belong to TurbineConfig.hot_start_s / warm_start_s / cold_start_s. The 60 must become 300 in the same commit as the backend change (D-08).

U-6. units_synchronised_count documentation is wrong and its meaning is changing. types.ts documents it as deriving from "state in synchronised/ramping/at_target"; the backend counts state == "synchronised" only. Both change under D-05.

What to add to the display

The current FleetTable presents a fleet that is already there. This algorithm's subject is units arriving and leaving.

Per-unit bar alongside CURRENT MW: fill output_mw / rated_mw, dashed rule at msl_mw / rated_mw, thin marker at setpoint_mw. The gap between marker and fill is the ramp — that gap closing is what "levels off at a stable state" looks like, and it is invisible today. For a STARTING unit the bar shows the sync countdown draining, labelled with thermal_state, start_phase and remaining time_to_online_s. UNLOADING is visually distinct from SYNCHRONISED so a unit leaving reads differently from a unit merely running low. BulletBar may fit — but its max must never derive from its own value.

Commitment stat rows, replacing the aggregate-ramp rows U-1 and U-2 invalidate: committed capacity against reserve_floor_mw; utilisation against the commit and decommit thresholds; and when a decision is blocked, blocked_by with last_decision_reason. An operator seeing no action needs to know whether the system is satisfied or constrained.

STARTING in the SYNC column. isOnBus() currently resolves to a breaker boolean. A starting unit is neither open-and-idle nor closed, and it is the state the operator most needs to see under this algorithm.
