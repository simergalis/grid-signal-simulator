IMPL-FC-HEADROOM-001 — Replit Agent Prompt

Fuel cell capacity excluded from kube admission headroom calculation

Root cause confirmed via manual trace (not yet filed): kube_demand.py line 358 computes headroom_mw = turbine_headroom_mw + bess_headroom_mw and never adds fuel cell capacity. The kube admission gate (power cap fires when headroom_mw < 2.5 MW) is therefore blind to up to fc_rated_mw of available headroom whenever a fuel cell asset is present and idle, causing the scheduler to stop admitting jobs earlier than the true power balance requires.

This prompt is split into two phases with a stop-and-report gate between them. Do not proceed past Phase 1 without an explicit go-ahead.

Phase 1 — Discovery (read-only, no files created or modified)

Answer the following. Cite file and line number for every claim. Do not propose a fix yet.

KubeGridState field inventory. Open the definition of KubeGridState (or equivalent struct feeding kube_demand.py). Does it already carry any fuel-cell-related field (rated capacity, current output, idle/standby flag)? List every field on the struct and where each is populated from. We need to know whether fuel cell state already flows into this struct for another purpose (e.g. the tile display) — if so, the fix should reuse that field rather than compute a second, parallel value. Flag this explicitly as a no-dual- implementation check.
Headroom semantics for turbine/BESS. For turbine_headroom_mw and bess_headroom_mw, trace how each is derived — is it simply rated capacity, or does it subtract something (ramp-rate limits, minimum state of charge, startup lag, reserve margin)? We need to know whether fuel_cell_headroom_mw should be a flat fc_rated_mw when idle, or whether it needs analogous derating (fuel cell startup time, minimum run constraints, fuel/H₂ availability) to stay consistent with how the other two asset classes are treated.
Where fc_rated_mw currently lives. Confirm the source of truth for fuel cell rated capacity in the scenario/asset config (field name, type, where it's loaded), and confirm whether it is None/absent when no fuel cell is configured for a scenario, vs. 0.0. This matters for the is not None discipline — the fix must not silently treat "no fuel cell" the same as "fuel cell rated at 0 MW" if those are meant to be distinguishable states.
All call sites of headroom_mw. List every place headroom_mw (or the function that computes it) is consumed, not just the admission-gate comparison at the line cited above. We need to confirm the fix doesn't have side effects elsewhere (e.g. a display value that currently matches the admission calculation and would silently diverge from it, or vice versa, if only the admission-path formula is changed).
Existing test coverage. Does any current test exercise the power-cap admission gate with a fuel cell present? If so, does it currently pass with FC capacity excluded (i.e., would it break if we add FC capacity into the sum), or does no test currently cover this path at all?

Stop here and report findings for all five items before any code is written.

Phase 2 — Implementation (gated on Phase 1 sign-off)

Once Phase 1 findings are reviewed and the derating question (item 2) is resolved:

Write the acceptance test first, structured to fail against current (pre-fix) logic:
Scenario with a fuel cell configured, BESS at or near exhaustion, and total headroom from turbine + BESS alone sitting just under 2.5 MW (admission gate should currently block).
Same scenario, but with fuel cell headroom included, total headroom should sit at or above 2.5 MW (admission gate should allow).
Assert the test currently fails pre-fix (confirms it's actually testing the defect, not a no-op). Report the failing assertion before proceeding.
Implement the fix per whatever Phase 1 established as the correct source field and derating treatment. Do not introduce a second computed value for fuel cell headroom if one already exists elsewhere in KubeGridState — reuse it.
Do not touch simulation_core.py's dispatch merit-order logic (BESS → FC → Grid). That logic is confirmed correct and out of scope for this fix.
Do not change the 2.5 MW power-cap threshold itself — only the headroom sum feeding the comparison against it.
Report the full suite delta (not just the new test) before this is considered done.
File this under docs/open-items.md as IMPL-FC-HEADROOM-001 once resolved, per the IMPL- prefix convention (implementation-level gap, distinct from the PSP-/CL- spec-gap registry).

Stop and report after the acceptance test is written and confirmed failing — before writing the fix itself.
