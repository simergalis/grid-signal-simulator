Two issues worth catching before Phase 4, one of them a real spec deviation.

least_recently_selected()'s alphabetical tiebreak contradicts §3.3.1. The spec is explicit: "lowest count first; ties broken by caller using priority class, then job age." That's a deliberate design choice — tie-breaking needs priority class and job age, information RotationState doesn't have and shouldn't need to have, since it only tracks selection_count. Putting an alphabetical tiebreak inside least_recently_selected() does two things wrong at once: it silently resolves ties on a criterion (tenant_id string order) that has no business meaning, and it removes the caller's ability to apply the one that does. This is the same failure shape as the grid/BESS pricing gaps — it produces a deterministic-looking, plausible answer that passes tests without being correct. TC-C9 as described ("lowest-selection_count tenant chosen among equally-eligible candidates") doesn't pin tie order, so it wouldn't catch this either. Concretely: a tenant whose tenant_id happens to sort late alphabetically is now permanently disadvantaged on every tie, forever, for a reason that has nothing to do with §30.7's fairness intent. Fix: least_recently_selected() should return the set of lowest-count candidates when there's a tie (or raise/require the caller to pass tiebreak criteria), not silently pick one. This needs to change before Phase 4 wires anything that depends on rotation fairness holding up under load.

persistence_backed=True in the demo scenario asserts something that isn't true yet. MT-4 says durability "is a stated requirement... but not yet implemented in any reference code," and the construction-time warning exists specifically to make that gap loud. But persistence_backed as built is just a boolean the caller sets — there's no actual store wired to it. Passing True in the scenario example (or anywhere, given no backing store exists yet) suppresses the warning while nothing durable is actually happening. That's worse than always warning, because it teaches whoever's calling this that setting the flag is sufficient, when what's needed is an actual persistence layer behind it. Two ways to close this cleanly: either require persistence_backed=True to come with a real store object (so the flag can't be set true without something backing it), or don't expose it as a settable boolean at all until MT-4's actual implementation lands — default it to False unconditionally and let the warning fire until there's something real to point it at. I'd rather see the demo scenario pass False and show the warning firing, since that's the honest state of the system right now.

One thing to confirm rather than fix: operating_tier as a keyword-only extension to evaluate() seems like the right call — BudgetGate is specified as pure with no side effects, so it can't look up "current operating tier" itself, and someone has to supply it. Just confirm the caller wiring this in Phase 4 is genuinely tracking §23.4 Ladder A state and not just threading through whatever value happens to be convenient at the call site — same "which value is authoritative" question as the season/month issue, just one level up the stack.

QuarantinedSignalError living in tenant_budget_gate.py is fine as defense-in-depth even though §17.2 quarantine conceptually belongs at schema-validation/ingestion — no objection there.

Fix the rotation tiebreak before Phase 4; the persistence flag can go either way but I'd rather it default honest. Neither blocks starting Phase 4's wiring work in parallel if you'd rather fix both alongside the grid-TOU extraction already queued for that phase's report.
