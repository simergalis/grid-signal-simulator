Phase 1 — Resolve the three drifts (decisions already made — DR-2026-08-06)

Each of these is two sources of truth returning different numbers for the same control-relevant quantity. The decisions are recorded; your job is to apply them and report, not to re-litigate.

pue_base — keep 1.03 in code; correct the catalogue.

Note the direction: the code wins here, not the catalogue. alpha_max already carries cooling separately (thermal.ts:89 — effective PUE = PUE_base × (1 + α_max)), so pue_base means IT-side overhead, not total facility PUE. At 1.11 the effective figure would be 1.332, which is a facility-wide number transcribed into a narrower slot.

Three edits, all required together:

gridsignal_parameters.json — set pue_base default to 1.03.
Same entry — revise the range from [1.05, 1.30] to one consistent with IT-side overhead, and rewrite the entry description to state which overhead it covers. The definition is the actual defect; the value is the symptom.
core/models.py:266 — correct the code comment, which cites a spec range of 1.02–1.05 matching neither document.

bess_rated_mw — take the catalogue's 15.0. renewable/config.py:61 holds an undocumented 10.0; the catalogue entry is VENDOR_RATING, the strongest provenance class present. If you find evidence the demo site's unit is genuinely 10 MW, stop and report rather than editing the catalogue — the provenance class would then also be wrong.

band_pct_calibrated — add band_enabled: bool; set the percentage to 4. The 0.0-means-disabled convention collides with a legitimate zero-width band, which is why the two sources disagree. A disabled state gets its own field. This is a schema change: core/models.py:289, the catalogue entry, and any consumer of the band logic.

Gate: Guard D1 green. Report each edit and confirm the catalogue and code now agree.

Do not proceed to Phase 2 without this. Migrating a literal to a runtime source while the two values disagree only relocates the disagreement.

Phase 2 — Backend runtime source

Wire core/site_parameters.py in and migrate the six D2 literals to read through it.

Preserve three properties of the loader as written:

Fail fast on an unknown key — ParameterNotCatalogued, never a default. A silently defaulted control-relevant parameter is a value chosen by nobody, which is the rule already applied to SiteLocation and to unknown persisted turbine states.
Provenance travels with the value. Most current entries are PROPOSED_HERE or ESTIMATE. Any surface that presents one as a measurement is the failure the catalogue exists to prevent.
CONFORMANCE entries are never editable. They are constant under acceptance test. A test already asserts this.

CFG-6 — inventory before promoting. 22 of the 36 catalogued keys have no matching literal anywhere in source. Guard D matches by name and cannot tell "unused" from "read under a different name". Classify all 22 before promoting D2, or the empty backlog is a claim nobody has verified.

Two follow-ups from the triage closeout, both in scope here because they are single-source-of-truth defects:

site_config._stored can be read unguarded. The closeout identified generate_solar_forecast() as reading _stored when called without an explicit site=. Its safety today rests on nobody having wired it into a run — a call-graph coincidence, not an invariant. Locate the function, report its signature, and make site a required parameter so an unguarded read becomes impossible rather than merely unlikely.
set_site_location() during an active run. PUT /api/location has no guard. Per the closeout recommendation, do not block it — the running simulation reads ctx.sim_state.site, not _stored, so the physics are safe and an operator may legitimately stage the next run's location. Add a warning log: "location changed while run is active; new location takes effect on next run start."

Gate: D2 backlog empty and CFG-6 inventory reported; promote D2 from reported to blocking. Full suite delta against 12/963/0.

Phase 6 — Peak site load (Class C — a decision, not a refactor)

PEAK_LOAD_MW = 23.95 at turbineFleet.ts:39 drives n1Covers, n1MarginPct, rampNeedMWs, and the READY/ATTENTION verdict. It is the most consequential number in the fleet modal and it is a literal.

Unlike Classes A and B, no source for it exists anywhere — not on ScenarioSpec, not on the tick, not in the catalogue. It stands in for a quantity the system does not model.

Decided (DR-2026-08-06): add design_peak_load_mw to ScenarioSpec and broadcast it. N−1 adequacy is a design-time question — can this plant survive a unit loss at its design load — not a question about the instantaneous load.

Interim, already implemented in siteParameters.ts: peakSiteLoadMW() returns the observed peak of p_compute_mw + p_cooling_mw over run history. It must be labelled "observed this run" — it understates early in a run, so an N−1 verdict computed against it reads optimistic until the site has seen its peak.

Gate: the N−1 verdict traceable to a declared or explicitly-labelled figure, with no literal anywhere in the path.
