Context

The simulator dashboard currently displays a forecast of 0.13 MW for a job whose declared full draw is 19.96 MW — an error of roughly 150×. The Forecast Quality panel reports the confidence band correctly (5% base + 8% uncalibrated = 13%, arithmetic verified) but has no data-quality flag capable of expressing "workload signal missing," so the failure is invisible.

Two further defects compound this:

The dashboard header shows PREDICTED PEAK 2.03 MW against SITE DRAW 1.80 MW — a 1.128× extrapolation of measured draw. Two different forecast values are displayed in the same run.
The BESS acts as the balance slack variable: grid_import_mw correlated with the negative of all other terms at +0.999999 in captured telemetry, so balance_residual_mw is zero by construction and validates nothing. Every model error surfaces as unexplained battery motion.

Constraint: no LLM, external API, or network dependency in any part of this work. All computation local and deterministic.

Phase 11.0 — Diagnostic only. Do not fix anything.

Instrument the forecast engine's input boundary and report. This phase gates every subsequent phase; the correct fix in 11.1 depends entirely on its outcome.

Add temporary structured logging at the forecaster input

For each forecast evaluation, emit one record containing:

tick, sim_time,
workload_signal_received      (bool)
workload_signal_age_s         (seconds since last WorkloadSignal, or null)
job_id
nodes_declared                (from the scenario/job record)
nodes_received                (Nodes_i(t) as seen by the forecaster)
hardware_profile_id
kW_per_node                   (kW_i resolved from the profile library)
pue_base
p_compute_computed_mw         (the Section 4 formula output)
p_compute_displayed_mw        (what actually reaches the UI)
measured_site_draw_mw
Report which branch is true

Compare nodes_received against nodes_declared and p_compute_computed_mw against p_compute_displayed_mw, then classify:

Branch A — signal absent. workload_signal_received is false. The forecaster never sees queue data and is extrapolating measured draw. This is an architectural defect.
Branch B — signal present, wrong magnitude. nodes_received is materially smaller than nodes_declared (check specifically for ~10 nodes against a job declaring hundreds; 10 nodes of enterprise_8gpu_air at PUE_base 1.03 yields 0.1051 MW, which is suspiciously close to the observed 0.13 MW). This is a scenario-to-engine wiring bug.
Branch C — computed correctly, displayed wrongly. p_compute_computed_mw is correct but p_compute_displayed_mw differs. This is a UI/plumbing defect.

Also report: what produces the header's PREDICTED PEAK, and whether it reads the same field as the Forecast Quality panel.

STOP

Post the diagnostic table and the branch classification. Do not proceed to Phase 11.1 without confirmation of which branch applies.

Phase 11.1 — Forecast path correctness

Apply the fix indicated by Phase 11.0. Regardless of branch, the following must hold when the phase closes.

Single source of truth

One field produces the forecast. The header, the Forecast Quality panel, and any other display read that same field. Two forecast numbers in one run is a defect.

The forecast is queue-derived, not telemetry-derived

Implement per Section 4: P_compute(t) = Σ_i Nodes_i(t) × kW_i × PUE_base, with Nodes_i(t) sourced exclusively from WorkloadSignal. The forecaster must not read measured site draw as a forecast input under any code path.

Acceptance criteria
#	Criterion	Threshold
F1	Forecast at job start vs Section 4 formula (TC-01 conditions: 10 nodes, enterprise_8gpu_air 10.2 kW, PUE_base 1.03)	0.1051 MW ± 0.1%
F2	Forecast for the demo job vs its declared allocation	within ±1%
F3	Inject a step change in measured site draw with no WorkloadSignal change	forecast changes by exactly 0.0 MW
F4	Header PREDICTED PEAK vs Forecast Quality centre value, same tick	bit-identical
F5	Forecast issued at starting event, not at full-TDP event (Section 6.1)	lead time ≥ Δt_lead

F3 is the load-bearing test. It is the assertable form of IP claim 1 — that the sensing point is predictive rather than reactive — and it is structurally the same assertion as TC-50, where fabric telemetry must produce no forecast change without a preceding WorkloadSignal.

Phase 11.2 — Add the missing data-quality flag class

Section 12's tag set currently has four flags: uncalibrated_site, unmapped_hardware, invalid_payload, stale_profile. None expresses an absent or stale workload signal, which is why a 150× forecast error was reported as a normal forecast with a ±0.02 MW band.

Add two flags
Flag	Trigger	CI widening
workload_signal_stale	No WorkloadSignal received within workload_signal_stale_s (default 30)	+20%
workload_signal_absent	No WorkloadSignal ever received for an active job, or the ingest connection is down	+50%

Widening values are chosen, not derived — state this in the panel exactly as the existing flags do.

Never-silent rule

When workload_signal_absent is set, the engine must not present a confident point forecast. Follow the Section 5.1 degradation discipline already used for unmapped hardware: conservative fallback value, visible tag, widened band, operator alert. Per the TC-43 pattern, a forecast carrying this tag must not drive autonomous curtailment.

Acceptance criteria
#	Criterion	Expected
Q1	Start a run with the WorkloadSignal source disconnected	workload_signal_absent ACTIVE, band widened ≥50%, operator alert raised
Q2	Stop the WorkloadSignal feed mid-run for > 30 s	workload_signal_stale ACTIVE within one tick of the threshold
Q3	Restore the feed	flag clears within one tick; band returns to prior width
Q4	Flags stack additively with existing flags	e.g. 5% base + 8% uncalibrated + 20% stale = 33%
Q5	Forecast tagged workload_signal_absent	no autonomous curtailment at any ladder tier
Phase 11.3 — Give the BESS a real command path

The battery must stop being the balance slack variable.

Split setpoint from measurement

Log bess_setpoint_mw (what dispatch arbitration commanded) and bess_measured_mw (what the plant model produced) as separate channels. Do the same for the turbine: gt_setpoint_mw and gt_measured_mw. Without this split, a controller bug and a plant bug are indistinguishable — which is why the −50.000000 MW rail behaviour in captured telemetry could not be attributed.

Close the balance on frequency, not on the battery

In islanded mode, frequency is the physically correct slack. Implement a swing equation:

df/dt = (P_gen - P_load) / (2 * H * S_base) * f_nominal

with H (system inertia constant, default 4.0 s), S_base (MVA base), and governor droop on the turbine (default 4%). In grid-connected mode, grid_import_mw remains the slack but must be reported as such in the schema.

balance_residual_mw then becomes a genuine model-error term rather than a definitional zero.

Acceptance criteria
#	Criterion	Threshold
B1	Inject a deliberate 1 MW error into the load model, islanded	frequency deviates measurably; balance_residual_mw is non-zero; BESS output does not silently absorb it
B2	corr(grid_import_mw, −(all other terms)), grid-connected	must not be ≥0.9999 unless grid_import is explicitly tagged as the slack term
B3	BESS output vs bess_setpoint_mw	tracks the setpoint within the modelled response time, never derived from the residual
B4	Step-load panel text vs live telemetry	if it says "BESS standby", bess_setpoint_mw must be ~0
B5	Rail saturation	when bess_setpoint_mw exceeds the rated limit, binding_constraint field is populated and surfaced

B4 exists because the panel previously read "BESS standby" while the battery moved 18.92 MW.

Phase 11.4 — Scenario configuration (YAML only, no code)
Compute-rack communication-phase floor: raise from 0.13 MW to 40–60% of peak (2.5–3.8 MW at a 6.3 MW peak).
Split deep valleys into a distinct checkpoint event: 15–30% of peak, 10–30 s duration, every 5–20 minutes. This is what Section 6.2's thresholds were designed to catch.
Scale generation to load, or load to generation — captured telemetry showed ~600 MW of generation against a 4.6 MW site.
Preserve the current profile as a separate named scenario grid_resonance_stress, with an assertion that its fundamental falls in the 0.1–0.2 Hz band.
Phase 11.5 — Complete the Forecast Quality panel

Do this after 11.1–11.3, and use it as the verification artifact for them.

Add to the panel
Plot the actual trace against the forecast band. The chart is titled "forecast vs actual" but currently shows only the forecast.
Empirical coverage: the fraction of actuals falling inside the band over the run. Without this, the band is unfalsifiable.
Forecast error: MAE and signed bias in MW.
Achieved lead time: measured interval between forecast issue and the load event arriving, which is the number the product's central claim rests on.
Extend the x-axis to cover at least the 30–60 s Section 28.1 horizon, and visually distinguish elapsed history from forecast-ahead.
Suppress or relabel uncalibrated_site in demo scenarios. It will be ACTIVE on every simulator run forever, and a permanently-lit flag trains operators to ignore the panel.
Acceptance criteria
#	Criterion	Threshold
P1	Empirical coverage on a clean calibrated run	within ±10 percentage points of the nominal band coverage
P2	Actual trace rendered and visually distinguishable from forecast	present
P3	Reported MAE vs independently recomputed MAE from the CSV	within ±1%
P4	Achieved lead time on the demo step-load	≥ 30 s, matching the headline claim
Phase 11.6 — Cooling thermal lag (IP claim 3)

Currently unimplemented: captured telemetry showed compute_inlet_temp_c with a lag-1 autocorrelation of +0.094 at 10 Hz, where a real thermal mass exceeds 0.99, and cooling load tracking compute instantaneously at a fixed 23.7% ratio.

Implement Section 8 as specified: Δt_thermal (default 90 s) and the α(t) first-order response, with the PUE decomposition into instantaneous baseline and delayed cooling components so the two are not double-counted.

Acceptance criteria
#	Criterion	Expected
C1	TC-02 — evaluate at t₀ + 60 s, below the 90 s default	P_cooling(t) = 0
C2	TC-03 — hold a constant job ≥ Δt_thermal + 5τ	converges to α_max × P_compute within 2% of asymptote
C3	compute_inlet_temp_c lag-1 autocorrelation at 10 Hz	≥ 0.99
C4	6-second load oscillation applied	cooling load does not pulse; it tracks the mean

C4 is a useful free consistency check: with a 90 s thermal lag, sub-band oscillation is filtered out by construction.
