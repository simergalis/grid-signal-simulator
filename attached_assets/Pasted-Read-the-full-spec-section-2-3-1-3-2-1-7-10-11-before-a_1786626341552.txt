## Q1 — PSP-5, winter TOU rates

**Recommendation: supply the real values now.** These two options aren't actually substitutes for each other, and treating them as either/or risks leaving PSP-5 unresolved past Phase 2:

- §11.3 requires PSP-5 "resolved, not merely stubbed" before design-partner use. An override mechanism doesn't resolve it — it defers resolution to a design partner who'd have to supply the same tariff data GridSignal can pull today.
- §7 already specifies what "resolved" means: "Full table, catalogued, cited, dated." That's a data-sourcing task, not an architecture decision.
- `PSP_STATUS_OVERRIDE` is a legitimate idea, but for a different problem: a design partner on a *different* utility or rate schedule than PG&E B-20. That's real and worth building eventually, but it's not blocking — don't let it absorb Phase 2's scope.

Current PG&E Schedule B-20 (secondary voltage), Cal. P.U.C. Sheet No. 61081-E, effective March 1, 2026:

| Period | Rate ($/MWh) |
|---|---|
| Winter Peak (4–9pm daily) | $156.32 |
| Winter Off-Peak (all other hours) | $114.60 |
| Winter Super Off-Peak (9am–2pm, **March/April/May only**) | $58.72 |
| Summer Peak (4–9pm daily) | $177.02 |
| Summer Part-Peak (2–4pm, 9–11pm) | $142.27 |
| Summer Off-Peak | $114.82 |

Two things this surfaces that you should know before Phase 2 writes code:

**1. The `season: Literal["summer","winter"]` signature in §3.2.1 can't express Super Off-Peak.** B-20 winter runs Oct 1–May 31, but Super Off-Peak only exists within March–May, 9am–2pm. `hour_of_day` + `season` alone can't distinguish "winter off-peak" from "winter super-off-peak" — you need month, not just season, to price Mar/Apr/May correctly. This is a real gap in the corrected interface, not just a data problem. Options: add a `month: int` parameter to `step()`, or have the caller resolve to a three-way `Literal["summer","winter","winter_super_off_peak"]` before calling. I'd lean toward passing `month` explicitly — it's the actual driver, and it's consistent with §3.2.1's own rule that the module doesn't read a clock but the caller derives everything from the simulated calendar.

**2. Voltage class (secondary/primary/transmission) isn't in your data contract at all**, and B-20 rates differ meaningfully by class (transmission demand winter peak is $2.97/kW vs. secondary's $2.32/kW, generation-only vs. bundled). A 5–50MW site is plausibly on primary or transmission service, not secondary. This should be a per-deployment catalogue parameter, same pattern as `fuel_cell_ppa_rate_mwh` — worth adding to §7's table now rather than discovering it when a real site's bill doesn't match your forecast.

I'd fold both of these into Phase 2's report rather than treating them as new open items — they're part of "supply the real winter table" done correctly, not scope creep.

## Q2 — PSP-6, BESS marginal cost

**Recommendation: A, with the parameters explicitly `PROPOSED_HERE` — not C's flat guess.**

B has a structural problem beyond being "cost-neutral": `cost_this_tick` and the economics screen need a marginal cost that means something on its own. If BESS cost is defined as *equal to whatever it's being compared against*, then any dollar figure recorded for BESS dispatch is circular — it reflects the other source's price, not the battery's economics. That corrupts the one downstream consumer (§10's economics screen, per your build queue) that this number exists to feed. It also does something worse operationally: it guarantees BESS never loses a cost comparison, which quietly biases `EconomicDispatchLoop`'s greedy allocation toward BESS on every tie, without that bias being visible anywhere in the code as a decision.

C's problem isn't the pattern (provisional + flagged is right, and matches how you're already handling `fuel_cell_ppa_rate_mwh`) — it's the number. A flat $12/MWh isn't in the neighborhood of any real BESS cost basis. I pulled current reference data:

- Lazard's 2025 LCOS (v10.0): 100MW/4-hour utility-scale unsubsidized BESS, $115–$254/MWh. That figure bundles in charging energy cost, though, which would double-count against whatever source actually charges the battery.
- Ember's Oct 2025 assessment, degradation/capex-driven only: $125/kWh all-in project capex, yielding roughly $65/MWh to move a unit of stored energy, excluding charge cost.

Running A's formula off that capex figure with a conservative 5,000-cycle LFP life: $125,000/MWh ÷ 5,000 cycles ≈ **$25/MWh** degradation, plus round-trip loss (~10–15% loss at ~$130/MWh grid cost) ≈ **$15–20/MWh**, giving a provisional total in the **$35–45/MWh** range — an order of magnitude above C's suggested $12, and directionally consistent with two independent public sources.

So concretely: adopt A's structure, source `battery_capex_per_mwh` and `cycle_life` from Lazard/Ember-class public references, tag both `PROPOSED_HERE` with citation and date exactly as §7 already does for `fuel_cell_ppa_rate_mwh`, and get explicit sign-off before Phase 3 wires `BudgetGate`. That satisfies §11.2's no-hardcoded-fallback rule, gives `cost_this_tick` a number that's actually about the battery, and is defensible enough to survive a design partner asking "where did this come from."
