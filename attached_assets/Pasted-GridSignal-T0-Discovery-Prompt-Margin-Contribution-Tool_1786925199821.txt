GridSignal — T0 Discovery Prompt: Margin Contribution Tool Integration Survey

Read this whole prompt before touching anything. This is a discovery task. You will not write, edit, or create any file. You will not fix anything you find broken along the way. You will answer the numbered questions below and report back — nothing else.

Context (short — you don't need the full spec for this)

We're adding a new operator-facing capability: before running a scenario, the operator configures energy cost estimates and per-tenant customer billing rates ("Economic Profile"). After a scenario completes, the operator generates a "Margin Contribution Proforma" — a report showing per-tenant and aggregate revenue, cost of energy, and margin, rolled up monthly/quarterly/annual.

This is a Scenario Planner-plane feature only. It reads a completed scenario's existing dispatch output; it does not re-simulate physics, and it must never influence dispatch, curtailment, or any control-plane decision.

To scope the implementation prompt correctly, I need you to answer the following questions about the current codebase. Cite exact file paths and line numbers wherever you can. If something isn't found, say so explicitly — "not found" is a valid and useful answer. Do not guess or infer an answer you can't point to in the code.

Questions
Scenario Planner entry point. Where is the Scenario Planner page implemented (component/file)? Where specifically does the existing "Run Scenario" control live, and is there an obvious place to add a second control ("Configure Economics") that's clickable before a run starts?
Dispatch output persistence. After a scenario run completes, where does the tick-level dispatch series live — MW drawn per source (grid firm/reserved/spot, turbine, BESS, solar) at each simulated tick? Database table, in-memory object, JSON blob, something else? Is it still accessible after the run completes without re-running the scenario, and for how long?
Per-tenant identity. Where are the three KubeDemandAgent tenant instances (A/SLURM, B/K8S, C/RAY) defined, and what fields identify a tenant in the scenario/dispatch output (id, name, weighting, scheduler type)? Is per-tenant metered usage (MW or MWh) already attributable from existing output, or would that require new instrumentation?
Config modal precedent. The GPU Node Generator modal (with its Queued/other tabs, per GS-IMPL-JOBQ-001) is the closest existing UI precedent for a multi-field configuration surface. Where is it implemented? What pattern does it use for persisting its configuration — component state, PostgreSQL, something else?
Scenario record schema. What table/model represents a completed Scenario run? What's its primary key / identifying scheme, and does it support versioning or is each run a fresh record with no revision history?
Existing report/export patterns. Is there any existing precedent in the codebase for the operator generating and exporting a report (PDF, CSV, on-screen table) from a completed scenario? If so, where, and what does it reuse (rendering library, download flow)?
Row-Level Security / tenancy scoping. Given the two-tier operator/site RLS schema used elsewhere (per GS-DES-TPCM-001), would a new Economic Profile table need an operator_id scoping column to follow the same pattern? Where is that pattern currently implemented, so a new table can match it exactly rather than improvising a variant?
Optional[float] / is not None override discipline. Is this enforced through a shared utility/helper, a lint rule, or convention-only (i.e., each module re-implements it)? Where's the best existing example to copy from?
Determinism test harness (AT-7). Where do the existing determinism tests live (the ones asserting bit-identical output for a given seed)? What's the pattern for asserting bit-identical output across repeated runs, so a Margin Contribution determinism test (NFR-30.2) can follow the same structure?
Reusable-template precedent. Is there an existing pattern anywhere in the app for a named, reusable, saved configuration object (something a user names, saves, and re-applies across multiple runs)? Or would an "Economic Profile" (reusable across scenarios) be net-new persistence design with no precedent to follow?
Do-not list for this task
Do not create, edit, or delete any file.
Do not write any code, even a stub.
Do not fix, flag-and-fix, or "clean up" anything you notice is broken — report it as an observation only.
Do not answer questions I didn't ask.
Do not propose an implementation approach. That's the next prompt, not this one.
If a question doesn't have a clean answer, say so and explain what you found instead of forcing a fit.
Report format

Answer each question in order, numbered to match. For each: the direct answer, file path(s) and line numbers as evidence, and "not found" stated explicitly where applicable. Close with a short section titled "Anything else relevant" for anything you noticed that doesn't fit the ten questions but would change how this feature should be scoped.
